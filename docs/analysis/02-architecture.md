# المعمارية المقترحة والقرارات التقنية المبكرة

> مقترح مبدئي للنقاش. كل بند هنا قابل للتغيير قبل بدء التنفيذ — لكن يجب حسمه **قبله** لا أثناءه.

## 1. القرار الأول (وأهم قرار في المشروع): نظام داخلي أم منتج؟

| | **نظام لشركة واحدة** | **منتج SaaS يُباع لعدة شركات** |
|---|---|---|
| العزل | فصل منطقي بسيط | عزل صارم متعدد المستأجرين + اختبارات تسرب |
| التخصيص | تعديل مباشر في الكود | إعدادات وقوالب لكل مستأجر — لا تعديل كود |
| النشر | نسخة واحدة | إصدارات، هجرات بيانات لكل مستأجر، لوحة تحكم للمزود |
| ZATCA | شهادات منشأة واحدة | إدارة شهادات لكل مستأجر ولكل وحدة إصدار |
| التكلفة | الأساس | **+٤٠٪ تقريباً** |

**لماذا يجب حسمه اليوم:** تحويل نظام أحادي إلى منتج متعدد المستأجرين لاحقاً يعني لمس كل استعلام في قاعدة البيانات.
التصميم لتعدد المستأجرين من البداية يكلف زيادة محدودة؛ إضافته لاحقاً يكلف إعادة كتابة.

**توصيتنا:** التصميم لتعدد المستأجرين منذ البداية حتى لو كان العميل الأول واحداً — الوثيقة نفسها تنص على
«تعدد الشركات والفروع»، وهذا نصف الطريق أصلاً.

## 2. نموذج العزل (Tenancy)

| النموذج | الوصف | متى نختاره |
|---|---|---|
| عمود `tenant_id` في كل جدول | قاعدة واحدة، فصل منطقي | الأبسط والأرخص — مع خطر تسرب عند أي استعلام يُنسى فيه الشرط |
| **Schema لكل مستأجر** | قاعدة واحدة، مخطط منفصل | **الموصى به** — عزل قوي، نسخ احتياطي واستعادة لكل عميل، تكلفة تشغيل معقولة |
| قاعدة بيانات لكل مستأجر | عزل كامل | للعملاء الكبار أو من لديهم متطلبات تنظيمية صارمة |

**الموصى به:** Schema-per-tenant، مع تطبيق **أمان على مستوى الصف (Row-Level Security)** كطبقة دفاع ثانية.
مبدأ الحماية: العزل يُفرض في طبقة البيانات، لا في كود التطبيق — لأن كود التطبيق ينساه.

## 3. الحزمة التقنية المقترحة

| الطبقة | المقترح | لماذا |
|---|---|---|
| **قاعدة البيانات** | PostgreSQL 16+ | معاملات ACID صارمة، `NUMERIC` دقيق للمال، RLS مدمج، JSONB للحقول المرنة، بحث عربي جيد |
| **الخلفية** | .NET 8 / C# أو NestJS (TypeScript) | كلاهما ناضج ومناسب. **.NET** أقوى في الأنظمة المالية وتوقيع XML وأدوات التشفير المطلوبة لـ ZATCA |
| **الواجهة** | React + TypeScript + دعم RTL أصلي | يطابق نماذج الواجهات المقدمة |
| **الجوال** | React Native أو Flutter | تطبيق واحد للموظفين (حضور، إجازات، مهام) + تطبيق POS إن لزم |
| **الطابور والمهام** | Redis + معالج مهام خلفية | ترحيل مؤجل، إرسال ZATCA وإعادة المحاولة، التقارير الثقيلة، الإشعارات |
| **الملفات** | تخزين كائنات متوافق مع S3 | المرفقات، ملفات XML وPDF/A-3، المخططات |
| **النشر** | Docker + Ubuntu Linux | يطابق ما نصّت عليه الوثيقة (§21) |
| **المراقبة** | تجميع سجلات + مقاييس + تتبع | متطلب تشغيلي منصوص عليه في الوثيقة |

> **مبدأ:** الحزمة أقل أهمية من الالتزام بها. أسوأ خيار هو خلط ثلاث حزم في مشروع واحد.
> إن كان لدى فريقكم الحالي خبرة راسخة في حزمة أخرى (Java/Spring, Laravel) فخبرة الفريق تتفوق على أفضلية الحزمة النظرية.

## 4. نمط المعمارية

**الموصى به: Modular Monolith** — تطبيق واحد بوحدات معزولة داخلياً بحدود واضحة، لا Microservices.

| | Modular Monolith | Microservices |
|---|---|---|
| المعاملات المحاسبية | معاملة قاعدة بيانات واحدة — **بسيط وصحيح** | معاملات موزّعة، Saga، تعويض — تعقيد كبير |
| التشغيل | نشر واحد | Service Mesh، اكتشاف خدمات، فريق بنية تحتية |
| مناسب لـ | فريق حتى ٢٠ مطوراً | فرق كبيرة موزّعة |

في نظام محاسبي، **التماسك المعاملاتي أهم من قابلية التوسع الأفقي**. قيد غير متوازن بسبب فشل جزئي في معاملة موزّعة
هو خطأ لا يُغتفر في هذا المجال. والوثيقة نفسها تقترح "Modular Architecture" (§21) وهذا يطابق التوصية.

الاستثناءان الوحيدان اللذان قد يُفصلان كخدمات مستقلة:
- **خدمة ZATCA** — لأن لها دورة حياة ومتطلبات أمنية (مفاتيح خاصة) مختلفة
- **خدمة التقارير** — لأنها تقرأ من نسخة قراءة منفصلة ولا يجب أن تُبطئ نظام الإنتاج

### حدود الوحدات المقترحة

```
Core/          الهوية · الصلاحيات · الشجرة التنظيمية · المستندات · سير العمل · التدقيق · الإشعارات
Ledger/        دليل الحسابات · القيود · الفترات المالية · العملات · التقارير المالية
Sales/         العملاء · عروض الأسعار · الفواتير · سندات القبض
Purchasing/    الموردون · طلبات الشراء · أوامر الشراء · فواتير المشتريات · سندات الصرف
Inventory/     الأصناف · المستودعات · الحركات · التكلفة · الجرد
Pos/           نقاط البيع · الورديات · الأجهزة الطرفية · المزامنة
Hr/            الموظفون · الحضور · الإجازات · الرواتب · الأداء
Projects/      المشاريع · BOQ · العقود · المستخلصات · المقاولون من الباطن · ضبط التكلفة
RealEstate/    العقارات · الوحدات · عقود الإيجار · التحصيل · الملاك
Assets/        الأصول الثابتة · المعدات · الإهلاك · الصيانة
Compliance/    الفوترة الإلكترونية · ZATCA · الإقرارات الضريبية
Portals/       بوابات العميل والمورد والمقاول
Ai/            OCR · الاقتراحات · التنبؤات   (مساعد فقط — لا صلاحية اعتماد)
```

**قواعد الحدود:**
- `Core` و`Ledger` لا تعتمدان على أي وحدة أعلى منهما — أبداً
- الوحدات الأفقية (Sales, Inventory, Hr) لا تستدعي بعضها مباشرة، بل عبر واجهات معلنة أو أحداث
- **لا وحدة تكتب في جداول `Ledger` مباشرة** — الكتابة عبر `Ledger.PostingService` فقط
- كل وحدة تملك جداولها؛ القراءة العابرة تكون عبر واجهات لا عبر `JOIN` مباشر

## 5. محرك القيود — العقد الأساسي

```
PostingService.Post(PostingRequest)
    ├─ يتحقق: الفترة المالية مفتوحة؟
    ├─ يتحقق: كل الحسابات موجودة وتقبل الترحيل (ليست حسابات تجميعية)؟
    ├─ يتحقق: مجموع المدين = مجموع الدائن (بعملة الشركة، بعد التحويل)؟
    ├─ يتحقق: النطاق مكتمل على كل سطر (شركة/فرع/مركز تكلفة حسب الإعداد)؟
    ├─ يخصص رقم قيد متسلسل لا تنكسر سلسلته
    ├─ يكتب القيد ورؤوسه وسطوره في معاملة واحدة
    ├─ يربطه بالمستند المصدر (نوع + معرّف)
    └─ يكتب سجل تدقيق
```

**قواعد غير قابلة للتفاوض:**
- القيد المرحّل **لا يُحذف ولا يُعدّل**. التصحيح بقيد عكسي فقط، ويبقى الأصل والعكس ظاهرين.
- ترحيل بأثر رجعي في فترة مقفلة: **ممنوع افتراضياً**، ويُسمح به فقط بصلاحية استثنائية موثّقة في سجل التدقيق.
- كل سطر قيد يحمل: الحساب، مدين، دائن، العملة، سعر الصرف، المبلغ بعملة الشركة، الفرع، المشروع، مركز التكلفة، البيان.
- **المبالغ `NUMERIC(19,4)`** في قاعدة البيانات و`decimal` في الكود. لا `float` ولا `double` في أي حقل مالي إطلاقاً.

## 6. الترقيم المتسلسل

مطلب نظامي (وZATCA تفرضه للفواتير). القواعد:

- تسلسل لكل (نوع مستند × شركة × سنة مالية) على الأقل
- **لا فجوات ولا تكرار** — التخصيص داخل معاملة قاعدة البيانات، لا في ذاكرة التطبيق
- لأجهزة POS العاملة دون إنترنت: **مدى محجوز مسبقاً لكل جهاز**، مع تسجيل الجهاز في النظام المركزي
- المستند الملغى **يحتفظ برقمه** ويُعلَّم كملغى — لا يُعاد استخدام الرقم

## 7. الأمن

| المتطلب | التنفيذ |
|---|---|
| المصادقة | OAuth2/OIDC + مصادقة ثنائية إلزامية للأدوار المالية |
| الصلاحيات | RBAC + ABAC: (دور × وحدة × عملية × نطاق × حد مالي) |
| العزل | Schema-per-tenant + RLS كطبقة ثانية |
| التشفير أثناء النقل | TLS 1.3 |
| التشفير أثناء التخزين | تشفير القرص + تشفير حقلي للبيانات الشخصية الحساسة (الهوية، الآيبان، الراتب) |
| المفاتيح الخاصة (ZATCA) | خزينة مفاتيح مخصصة أو HSM — **لا تُخزَّن في قاعدة بيانات التطبيق ولا في ملفات الإعداد** |
| سجل التدقيق | غير قابل للتعديل، لكل عملية، مع القيمة قبل/بعد والجهاز وعنوان IP |
| النسخ الاحتياطي | يومي كامل + سجلات معاملات مستمرة، مشفّر، **مع اختبار استعادة دوري موثّق** |
| فصل البيئات | تطوير / اختبار / إنتاج منفصلة تماماً — ولا بيانات إنتاج حقيقية في بيئات الاختبار دون إخفاء هوية |

## 8. الأداء

النقاط التي تنهار عندها أنظمة الـ ERP المحاسبية عادةً:

| المشكلة | المعالجة |
|---|---|
| ميزان المراجعة يمسح ملايين السطور | جداول أرصدة مجمّعة محدّثة عند الترحيل (`account_period_balances`) |
| التقارير الثقيلة تُبطئ الإنتاج | نسخة قراءة (Read Replica) مخصصة للتقارير |
| نمو جدول القيود بلا حد | تقسيم أفقي بالفترة المالية (Partitioning) وأرشفة السنوات المغلقة |
| ذروة إغلاق الشهر | معالجة الترحيل الجماعي عبر طابور غير متزامن |
| بحث عربي بطيء | فهارس نصية مع تطبيع الهمزات والتاء المربوطة والتشكيل |

## 9. التدويل و RTL

- **العربية هي اللغة الأساسية، لا الترجمة الثانية.** الواجهة تُصمَّم RTL أصلاً، ولا تُعكس بـ CSS لاحقاً.
- كل جدول بيانات تأسيسية يحمل `name_ar` و`name_en` — وليس جدول ترجمات منفصلاً يُنسى ملؤه.
- التاريخ: تخزين ميلادي دائماً في قاعدة البيانات؛ العرض حسب تفضيل المستخدم (هجري/ميلادي) — والتقويم الهجري
  في المملكة له متطلبات خاصة في الرواتب والإجازات وحساب نهاية الخدمة.
- الأرقام: تخزين لاتيني، وعرض حسب التفضيل (عربي/هندي).
- التقارير والفواتير المطبوعة: قوالب RTL بخطوط عربية مضمّنة (لتفادي تشوّه الخط عند التصدير إلى PDF).
