# الفوترة الإلكترونية والالتزام الضريبي (ZATCA)

> **تنبيه مهم:** ما يلي فهم أولي لمتطلبات هيئة الزكاة والضريبة والدخل بغرض التخطيط والتقدير.
> **يجب التحقق من كل تفصيلة تقنية مقابل المواصفات الرسمية المنشورة على بوابة «فاتورة» وقت التنفيذ**،
> لأن المواصفات وقوائم التحقق تُحدَّث دورياً. وثيقة العميل نفسها نصّت على هذا التحفظ (§5) وهو تحفظ في محله.
>
> لا يُبنى أي كود تكامل نهائي اعتماداً على هذه الوثيقة وحدها.

## 1. لماذا هذا الجزء يستحق أولوية مبكرة

الفوترة الإلكترونية **ليست ميزة إضافية** — هي شرط قانوني لممارسة النشاط. النظام الذي لا يُصدر فاتورة مقبولة
من الهيئة لا يمكن إطلاقه تجارياً، مهما كانت بقية وحداته ممتازة.

وهي أيضاً **الجزء الأكثر احتمالاً لمفاجآت تقنية**: شهادات، توقيع تشفيري، بيئات اختبار، قوائم تحقق تُرفض
لأسباب دقيقة (ترتيب عناصر XML، تنسيق التاريخ، تقريب مبلغ).

**لذلك: إثبات مفهوم (PoC) على بيئة المحاكاة في الشهر الأول من المشروع، لا في مرحلة الاختبار.**
اكتشاف عائق هنا في الشهر الأول = تعديل خطة. اكتشافه في الشهر العاشر = تأجيل الإطلاق.

## 2. المرحلتان

| | **المرحلة الأولى — الإصدار** | **المرحلة الثانية — الربط والتكامل** |
|---|---|---|
| الجوهر | إصدار الفواتير إلكترونياً بصيغة منظمة | ربط النظام مباشرة بمنظومة الهيئة |
| المطلوب | فاتورة إلكترونية منظمة + رمز QR للمبسطة + منع التحرير اليدوي | XML بمعيار UBL 2.1 + ختم تشفيري + UUID + تجزئة الفاتورة السابقة + إرسال للهيئة |
| التطبيق | إلزامي على الجميع | على مجموعات (Waves) حسب حجم الإيرادات — تُبلَّغ المنشأة بموعدها |

**النظام الجديد يجب أن يُبنى للمرحلة الثانية مباشرة.** بناء المرحلة الأولى فقط يعني إعادة عمل مؤكدة.

## 3. نوعا الفاتورة ومساراهما — أهم فرق تصميمي

| | **فاتورة ضريبية (Standard / B2B)** | **فاتورة ضريبية مبسطة (Simplified / B2C)** |
|---|---|---|
| المسار | **المقاصة — Clearance** | **الإبلاغ — Reporting** |
| التوقيت | **قبل** تسليمها للمشتري | **خلال ٢٤ ساعة** من إصدارها |
| الأثر | الهيئة تعيدها مختومة بختمها؛ **النسخة المعتمدة هي التي تعيدها الهيئة** | تُسلَّم للعميل فوراً؛ الإبلاغ يتم بعدها |
| عند الرفض | **الفاتورة غير صادرة قانوناً** — لا تُسلَّم للعميل | صدرت فعلاً؛ الرفض يستوجب معالجة وتصحيحاً |
| بيانات المشتري | مطلوبة (رقم ضريبي، عنوان) | مبسّطة |
| رمز QR | مطلوب حسب المواصفة | **مطلوب دائماً** |

**الأثر المعماري:**
- الفاتورة الضريبية العادية = عملية **متزامنة حاجزة**: لا تُطبع ولا تُرسل للعميل قبل رد الهيئة.
  واجهة المستخدم يجب أن تتعامل مع حالة انتظار، وحالة رفض، وحالة انقطاع اتصال.
- الفاتورة المبسطة (وهذا مسار POS) = عملية **غير متزامنة**: البيع يكتمل، والإبلاغ يجري في طابور خلفي.
  **وهذا ما يجعل POS دون إنترنت ممكناً أصلاً.**

## 4. عملية التسجيل والشهادات (Onboarding)

كل **وحدة إصدار (EGS Unit)** — أي جهاز أو نقطة إصدار فواتير — تُسجَّل مستقلة ولها شهادتها الخاصة.

المسار العام:

```
1. توليد مفتاح خاص وطلب توقيع شهادة (CSR) للوحدة
2. الحصول على رمز OTP من بوابة فاتورة
3. طلب شهادة الامتثال (Compliance CSID)
4. اجتياز فحوصات الامتثال (إرسال فواتير اختبارية بأنواعها)
5. طلب شهادة الإنتاج (Production CSID)
6. الوحدة جاهزة للإصدار الفعلي — مع تجديد دوري للشهادة
```

**الآثار التشغيلية التي يجب تصميمها في النظام:**

| الأثر | المتطلب |
|---|---|
| ٥٠ نقطة بيع = ٥٠ وحدة إصدار | **شاشة إدارة وحدات الإصدار** داخل النظام: تسجيل، تجديد، إبطال، متابعة حالة |
| المفاتيح الخاصة حسّاسة | تخزين في خزينة مفاتيح أو HSM — **لا في قاعدة البيانات ولا في ملفات الإعداد ولا في مستودع الكود** |
| الشهادات تنتهي | تنبيهات تجديد آلية قبل الانتهاء بمدة كافية |
| بيئات متعددة | فصل كامل بين بيئة المحاكاة وبيئة الإنتاج — شهادات وإعدادات ومسارات مستقلة |

## 5. مكوّنات الفاتورة الإلكترونية

| المكوّن | ملاحظات التنفيذ |
|---|---|
| **XML بمعيار UBL 2.1** | حساس لترتيب العناصر وتسميات المساحات (Namespaces). التوليد بمكتبة موثوقة والتحقق مقابل المخطط قبل الإرسال |
| **UUID** | معرّف فريد لكل فاتورة، منفصل عن رقم الفاتورة التسلسلي |
| **الترقيم المتسلسل** | متسلسل بلا فجوات لكل وحدة إصدار |
| **تجزئة الفاتورة السابقة (PIH)** | كل فاتورة ترتبط بتجزئة سابقتها في **سلسلة لا تنكسر لكل وحدة إصدار**. أي كسر يبطل السلسلة |
| **الختم التشفيري** | توقيع رقمي بالشهادة المرتبطة بالوحدة |
| **رمز QR** | ترميز TLV مشفّر Base64. الحقول الأساسية: اسم البائع، الرقم الضريبي، الطابع الزمني، الإجمالي شاملاً الضريبة، إجمالي الضريبة — وتُضاف حقول التوقيع والتجزئة والمفتاح العام في المرحلة الثانية |
| **الأرشفة** | حفظ XML الأصلي ورد الهيئة وحالته. **مدة الحفظ النظامية يجب التحقق منها في اللائحة السارية** |

> **الخطر الأكبر عملياً هو سلسلة PIH.** في POS يعمل دون إنترنت مع أجهزة متعددة،
> يجب أن تُبنى السلسلة **محلياً على كل جهاز بالترتيب الصحيح**، وألا تنكسر عند المزامنة المتأخرة أو إعادة الإرسال.
> هذا يحتاج تصميماً صريحاً واختباراً مقصوداً لسيناريوهات الانقطاع.

## 6. الإشعارات الدائنة والمدينة

- لها نفس متطلبات الفاتورة (XML، ختم، إرسال) وتتبع نفس مسار أصلها (مقاصة أو إبلاغ)
- يجب أن تُشير إلى **الفاتورة الأصلية** وسبب الإصدار
- في النظام: كل إشعار مرتبط بفاتورته، ويولّد قيداً عكسياً جزئياً أو كلياً

## 7. معالجة الأخطاء — ما يُنسى دائماً

| الحالة | السلوك المطلوب |
|---|---|
| رفض فاتورة مقاصة | الفاتورة **غير صادرة**. عرض سبب الرفض بلغة مفهومة، منع التسليم، السماح بالتصحيح وإعادة الإرسال |
| فشل إرسال فاتورة مبسطة | إعادة محاولة تلقائية بتباعد متزايد، مع سقف زمني ثم تنبيه بشري قبل انقضاء الـ ٢٤ ساعة |
| انقطاع طويل عن الهيئة | طابور متراكم + **لوحة متابعة تعرض عدد الفواتير غير المبلَّغة وأقدمها** — مؤشر مخاطرة يجب أن يراه المدير المالي |
| كسر سلسلة PIH | تنبيه فوري بأعلى درجة — هذا خلل يوقف الإصدار على الوحدة المتأثرة حتى المعالجة |
| اختلاف بين الإقرار والمرسل | تقرير مطابقة دوري بين حركات حسابات الضريبة وسجل الفواتير المرسلة |

**مبدأ:** لا تُبتلع أخطاء الهيئة بصمت في سجل فني. كل فاتورة لها **حالة إرسال ظاهرة للمستخدم**
(في الانتظار / مقبولة / مقبولة بملاحظات / مرفوضة / فشل الإرسال) ولوحة متابعة مخصصة لها.

## 8. تصميم الوحدة داخل النظام

```
Compliance/
  ├─ EgsUnits/          تسجيل وحدات الإصدار وإدارة دورة حياة الشهادات
  ├─ InvoiceBuilder/    تحويل مستند الفاتورة الداخلي إلى UBL 2.1 XML
  ├─ Signer/            التجزئة والختم التشفيري وبناء رمز QR
  ├─ Chain/             إدارة سلسلة PIH لكل وحدة إصدار
  ├─ Transport/         الاتصال بواجهات الهيئة (مقاصة / إبلاغ) وإعادة المحاولة
  ├─ Archive/           حفظ XML ورد الهيئة والحالة
  └─ Reporting/         الإقرار الضريبي وتقارير المدخلات والمخرجات والمطابقة
```

**قرار مطلوب من المالك:** التعامل المباشر مع واجهات الهيئة، أم عبر **مزوّد حلول معتمد**؟

| | مباشر | عبر مزوّد معتمد |
|---|---|---|
| التكلفة | جهد تطوير أعلى مقدماً | رسوم دورية لكل فاتورة أو اشتراك |
| التحكم | كامل | محدود بواجهة المزوّد |
| مواكبة تحديثات المواصفة | مسؤوليتنا | مسؤولية المزوّد |
| مناسب لـ | منتج يُباع لعدة عملاء | إطلاق أسرع وتقليل المخاطرة التنظيمية |

## 9. خطة إثبات المفهوم المقترحة (الشهر الأول)

1. تسجيل وحدة إصدار تجريبية على **بيئة المحاكاة**
2. توليد فاتورة ضريبية عادية بمعيار UBL 2.1 واجتياز المقاصة
3. توليد فاتورة مبسطة واجتياز الإبلاغ
4. توليد إشعار دائن مرتبط بفاتورة سابقة
5. بناء سلسلة PIH لعشر فواتير متتالية والتحقق من سلامتها
6. **محاكاة انقطاع اتصال** ثم استئناف المزامنة والتحقق من عدم كسر السلسلة
7. توليد رمز QR والتحقق منه بأداة تحقق مستقلة

**مخرج إثبات المفهوم:** تقرير جدوى يؤكد أو ينفي التقديرات، ويحدد المخاطر الفعلية قبل تثبيت الخطة والميزانية.
